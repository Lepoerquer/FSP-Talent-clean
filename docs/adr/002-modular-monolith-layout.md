# ADR 002: Организация модульного монолита (Modular Monolith)

## Статус
Принято (Accepted)

## Контекст
В условиях ограниченного времени хакатона распределенная микросервисная архитектура создает чрезмерные накладные расходы на сетевое взаимодействие, distributed tracing, согласованность транзакций и DevOps. В то же время классический "спагетти-монолит" приводит к конфликтам кода и размыванию ответственности между бэкенд-инженером (Р1) и ML-инженером (Р2).

## Решение
Использовать архитектуру **модульного монолита** с физическим разделением доменов внутри каталога `backend/app/modules/`:

1. `auth` - аутентификация, валидация JWT токенов, управление сессиями и правами.
2. `users` - пользователи платформы, роли (кандидат, представитель компании, администратор).
3. `consents` - версионирование согласий по 152-ФЗ (обработка ПДн, распространение данных), журнал согласий и отзыв.
4. `profiles` - анкета кандидата, настройки видимости, скрытие от конкретных компаний.
5. `companies` - профиль компании-работодателя, привязка сотрудников.
6. `dictionaries` - справочники направлений, специализаций, грейдов с поведенческими индикаторами, 300+ навыков с синонимами, матрица смежности.
7. `assessment` - банк семейств заданий, генерация изоморфных экземпляров по seed, сессии тестирования (CAT), алгоритм 2PL IRT, оценка способности $\theta$ и погрешности SE.
8. `categorization` - правила присвоения категории (специализация × грейд), правила подтверждения, повышения, понижения и ограничение 90 дней на смену грейда.
9. `matching` - двухэтапный подбор кандидатов по потребности работодателя, скоринг по объяснимой формуле, генерация снимков подборки (snapshots), шорт-листы.
10. `invitations` - модель и конечный автомат приглашений с обязательной зарплатой "от-до" в рублях, сокрытие контактов до принятия, аудит-лог.
11. `fsp` - интеграция с реестром ФСП, расчет FSP-score, деликатная обработка кандидатов без истории ФСП (бонусная, а не штрафная логика).
12. `notifications` - отправка оповещений (email через Mailpit/SMTP, websocket/in-app).

Каждый модуль инкапсулирует:
- `models.py` - SQLAlchemy сущности;
- `schemas.py` - Pydantic схемы валидации;
- `service.py` - бизнес-логика модуля;
- `router.py` - эндпоинты FastAPI.

Межмодульное взаимодействие осуществляется через вызовы сервисных интерфейсов без прямых циклических зависимостей в БД.

## Последствия
- Высокая изоляция доменов: Р1 разрабатывает платформенные модули (`profiles`, `invitations`, `consents`), а Р2 реализует логику в `assessment` и `matching`.
- При необходимости масштабирования любой модуль может быть выделен в отдельный микросервис без изменения внешнего API.
